# Pith for Mac

Pith is the native menu bar version of Storage. It combines current activity, ten minutes of session history, and the existing Rust disk scanner and React treemap. The name is provisional.

## Build and open

From the repository root on a Mac with Xcode 26 or later, Rust, Node and pnpm installed. The command-line tools alone aren't enough: the app icon is an Icon Composer package, which only Xcode 26's `actool` compiles.

```sh
pnpm build:pith
pnpm open:pith
```

The app is at `apps/storage/native/.build/Pith.app`. You can drag it to Applications. It is built for the current Mac's architecture, targets macOS 14+, and has been run locally on Apple Silicon/macOS 26.3. Older macOS versions and Intel need their own verification before release.

`build:pith` signs the app, its bundled scanner and Sparkle ad hoc, with the hardened runtime, so it runs on the Mac that built it. Ad hoc code belongs to no team, so this build alone turns off the runtime's library validation, which would otherwise refuse to load Sparkle. It has no update feed and never updates. Rebuilding an ad-hoc app can invalidate its privacy grants; grant Full Disk Access to the installed app when a partial scan needs it.

### Release

A version is a section of [`CHANGELOG.md`](CHANGELOG.md): the newest section's number is the version the build stamps (as both `CFBundleShortVersionString` and the `CFBundleVersion` Sparkle compares), and its notes are what Pith's update window shows. The build refuses notes with bullets or dashes, and versions out of order.

```sh
pnpm --filter storage release:mac
pnpm --filter storage publish:mac --dry-run
pnpm --filter storage publish:mac
```

`release:mac` signs the app, the scanner and Sparkle with the keychain's Developer ID Application certificate and Apple's secure timestamp, sends the app to Apple's notary service, staples the ticket so it opens offline, checks that Gatekeeper accepts it, and leaves the download at `apps/storage/native/.build/Pith-<version>.zip`. It stops with Apple's log when notarization isn't accepted. It records the commit it was built from in the app. It needs a notarytool keychain profile, stored once from an App Store Connect API key:

```sh
xcrun notarytool store-credentials pith-notary --key AuthKey_<key ID>.p8 --key-id <key ID> --issuer <issuer ID>
```

`PITH_SIGN_IDENTITY` picks the certificate when the keychain has several, and `PITH_NOTARY_PROFILE` names another profile. A release is built for the building Mac's architecture only.

`publish:mac` checks that the download is the changelog's newest version, notarized, built from a commit on `origin/main` without uncommitted changes, and newer than the feed's newest. It then creates the GitHub release `pith-v<version>` with the download and puts the version on top of the update feed, `appcast.xml` in the `pith-updates` pre-release. A release of its own keeps the feed's address fixed whatever becomes the repository's latest release. Before uploading, it signs the download and the feed with the update key, and after, it checks GitHub serves both as signed. With `--dry-run` it uploads nothing.

The update key is an EdDSA key pair. Its public half is `PUBLIC_KEY` in `scripts/pith-release.mjs`, which every release trusts; its private half is in the publisher's login keychain under the account `pith`, and macOS asks once to let Sparkle's `sign_update` use it. `generate_keys --account pith` (in `native/.build/artifacts/sparkle/Sparkle/bin`) makes the pair once, and prints the public half again any time. Keep a copy somewhere safe, such as a password manager: `generate_keys --account pith -x <file>` exports it and `-f <file>` imports it on another Mac. A lost key means installed copies accept the next update only through a Developer ID signed disk image, as Sparkle's key rotation allows.

## Use

- The menu bar shows the bruh-slice glyph and system CPU. While memory pressure is elevated or critical, its symbol appears in its status colour, also in icon-only mode.
- Click the item for the panel: CPU and memory pressure over the last ten minutes, the busiest apps, and free space on the startup disk. Click an app to open it in Activity, or the disk row to open Disk. Settings and Quit are under the ⋯ button.
- Activity and Disk are tabs of one window (⌘1 and ⌘2). Activity lists apps with live CPU, memory, power, disk reads and writes, and network use, updated every second while it's open; search with ⌘F and include apps that quit in the last ten minutes from the filter menu. Drag across the CPU chart to rank apps by that time instead of now, and press Escape or Back to Live to return. The inspector (⌥⌘I) shows the selected app's history, processes, path, and Reveal in Finder and Quit. Charts mark when apps opened.
- Disk shows the startup disk's map, which Pith keeps current by itself: it maps the disk once, the first time Disk opens, and from then on re-reads only the folders that change. Choose Folder shows a folder of the startup disk from the same map at once, and scans a folder on another disk, or one the map couldn't read. Larger blocks occupy more space and their colour shows the kind of file. Select a block or largest-file entry, double-click a folder to explore, or use the accessible item list with the keyboard. The map shows what grew since the day before and, with Keep a week of history on, which apps wrote the most to disk meanwhile. Bigger Text zooms the map too.
- Shortcuts and Siri have Get Busiest Apps, Get Memory Pressure, Show Activity and Scan Folder.
- Move to Trash is a native, confirmed action on an entry from the current map. Protected paths and paths escaping the map's root are rejected. Finder's Put Back restores trashed files. A successful move takes the item off the map at once, and the live map then follows the move itself.
- Closing the window keeps monitoring. Quit ends monitoring and clears session history. Login startup and icon-only mode are opt-in in Settings. Reopen the app from Finder to recover Activity if macOS hides the menu bar item.
- A release updates itself. At its second launch it asks whether it may check for updates once a day, and whether to install them by itself too; Settings changes both. Check for Updates… is in the panel's gear menu and the app menu. A newer version a daily check finds waits on the panel's last line rather than opening a window over other apps; the update window shows its notes and installs it, quitting and reopening Pith.
- Pith follows the system appearance: light, dark and Increase Contrast.

## Logo

Pith's mark is the bruh mascot as a lemon slice. `scripts/brand.mjs` generates everything in `Brand/` from the bruhs colour tokens and the shared mascot geometry (`packages/ui/src/lib/logo.ts`):

- `AppIcon.icon`: the Icon Composer app icon, with the slice and the face as separate layers so macOS can render its light, dark, clear and tinted styles.
- `StatusGlyph.svg`: the menu bar template image.
- `pith-mark.svg` and `pith-wordmark.svg`: the mark and the wordmark (the mark plus "pith" in Monaspace Krypton, outlined).

After changing a token or the mascot, run `node scripts/brand.mjs` in `apps/storage` and commit the result. `pnpm check:pith` fails while `Brand/` is out of date. You can open `AppIcon.icon` in Icon Composer to preview it, but edits made there are overwritten the next time the generator runs.

## Icons

Pith shows the icons macOS draws for real things on this Mac, asking for them as it runs: an app's own icon, a folder's, a disk's and a file type's. It ships none of Apple's art. It never reads CoreTypes' `.icns` files, which are stale on macOS 26, or uses the undocumented `com.apple.graphic-icon.*` and `com.apple.application-icon.*` types, and Apple's icons and SF Symbols stay out of Pith's own icon, logo and website.

Each icon has a key that says where it comes from (`IconKey`). A file's is `type/<extension>`, from its type alone, so Pith never opens the file. A folder, package, app or volume the map has read is `item/<path>`, drawn as Finder shows it, its custom colour or emoji included. A known place is `place/<id>`: `KnownPlaces` gives Documents, Downloads, Desktop, Applications and the Trash their special folders' types, and Photos Library, Mail, Messages, Developer, iCloud Drive, Music, TV, Books and Podcasts the icons of the apps they belong to, each confirmed on this Mac, with a plain folder as the last fallback. A folder the map couldn't read is `folder`, and the map's smaller items are `group`. Inside a location macOS guards, such as Desktop, Documents, Downloads, iCloud Drive, other apps' containers, the Photos library, Mail and Messages, Pith looks a folder up by its path only when the map shows it has listed it, with a size, files or contents, and only while macOS is asking about none of the map's folders and the map isn't catching up after a launch. The live map shows a folder it has found in its parent's listing, but not yet listed itself, as empty, and macOS may be holding that listing, so such a folder shows a plain folder there, as an empty one does.

`IconStore` draws every icon off the main thread, four to eight at a time, with iCloud downloads off for its threads, as the scanner turns them off for its process. It draws each icon in the light or dark appearance asked for, since macOS picks an icon's artwork as it draws it, and keeps up to 16 MiB of drawings by key, appearance and size. The bar under the disk map leads with the selected item's icon. Activity's app icons are NSWorkspace's own images, which draw themselves in each row's appearance.

## Data and architecture

SwiftUI/AppKit owns the menu bar, Activity window, sampler, history, folder picker and file actions, including Move to Trash and its Undo. Rust keeps the startup disk's live map in a long-running `storage-scanner serve` process, and runs the one-off scans of other disks. The disk renderer reuses the existing React components in a WKWebView created when Disk first opens, kept while the window is open so the map keeps its place across tabs, and released on close. It ships as static local assets with no Node server, listening socket, remote page, telemetry or network dependency.

The scanner stays on the scanned folder's file system and counts the startup disk's firmlinked folders (`/Users`, `/Applications` and the rest of `/usr/share/firmlinks`) once, at their visible paths, rather than again under `/System/Volumes/Data`. Volumes mounted inside a scan are shown as blocks sized from their own used space when they share the scanned disk (Preboot, VM) and are otherwise left out, found in the mount table and never opened: macOS asks the person about network and removable volumes, and the automount every Mac has at `/System/Volumes/Data/home` counts as a network volume. It turns off iCloud downloads for its own process before reading anything, counts files that aren't downloaded without opening them, and keeps every folder it can't read in the result with its reason. Move to Trash refuses the system's top-level folders, the home folder and its vital folders by file identity, so no path can reach them.

APFS clones count once. Files that share every block (`EF_SHARES_ALL_BLOCKS`) and the same clone ID form a group, and its bytes count at the copy made first, the lowest inode, whichever order the parallel walk reaches them in. Folders report the bytes of their other copies as clones. Clones changed since they were made share only some blocks and still count at every copy. Selecting an item asks the scanner what deleting it frees now: each file's private size (`ATTR_CMNEXT_PRIVATESIZE`), plus clone groups and hard-linked files whose every copy is inside it. Reading private sizes costs about half again a listing, so a scan never does.

The startup disk's map is live. `storage-scanner serve` holds an index of every folder: its totals for everything beneath it, its inode, and its files of 1 MiB or more by name, so a change costs a listing of the changed folder and an update of each folder above it. Pith streams FSEvents for `/` with file-level events and each item's inode (`LiveStream`), and passes them on. The scanner lists a changed folder again once it has settled for three seconds, and a folder whose listing was slow waits 200 times as long before its next, which keeps a busy cache of tens of thousands of files under half a percent of a core. A folder that left its parent waits in limbo for five minutes, so a move found in the other folder's listing is carried over by inode rather than scanned again. Only a parent's listing decides whether a folder is still there: one gone from its path has its parent listed, and is listed again if it turns up back in the tree, and an event inside a folder that moved off finds it again by an item's inode. Hard links and full clones count once, as in a scan. Each record of where one counts carries its folder's generation, which moves on with every listing of that folder, so a listing retires what it no longer finds without the index keeping every file. Each clone group also keeps a runner-up, which takes the bytes when the holder goes, as when a folder of Finder copies stays after its originals are deleted.

The index is saved to `~/Library/Application Support/Pith/Scans/startup-disk.index` every half hour while it changes, before sleep, and at quit, which waits up to five seconds for the scanner to save and exit, with the event ID through which every change is in it: 20 to 23 MB of LZFSE frames for the development Mac's 1.2 million folders, written in under a second and closed by a hash, so a damaged file is refused whole. At launch Pith opens it in under a second and replays FSEvents' history from that ID, which took 0.2 to 3.8 s after a relaunch. It walks the disk again instead when the volume's FSEvents UUID changed, the IDs started over, more than ten million IDs passed, or the history doesn't reach back to the save. With nothing saved, the first walk waits until Disk opens, since it can bring macOS's permission questions. Opening a folder macOS protects waits until the person answers, however long that takes, so a listing still opening after half a second gets a thread in its place, and the folders likely behind the same question wait behind three probes: those beside it, and those of its name beside its parent, as every app container's Data folder is. The map is done once only those folders remain. Disk says macOS is asking about them, and each joins the map when the person answers. The wait isn't counted as the listing's cost, which sets how soon a folder is listed again. A lock beside the file keeps a second copy of Pith from saving over it. Every minute the scanner checks the 200 largest files and the volumes inside the map that share its disk for growth FSEvents can't report, since a file held open raises an event only once it's closed. Once a day, on power, outside Low Power Mode and not running hot, `NSBackgroundActivityScheduler` has it list every folder again on two background threads with throttled I/O, and report how far off the map had drifted. macOS keeps that schedule across launches, so an overdue check comes as Pith opens: it waits until the map has caught up, and skips a day in which a walk or a check already listed every folder. A check waiting only on folders macOS is asking about ends with what it found. A folder on another disk is still scanned once, followed with FSEvents from the event ID its scan began at, and caught up with Refresh, which scans the changed folders again, or the whole folder when FSEvents lost track or more than 24 changed. Pith doesn't keep those maps between launches.

System CPU uses deltas of host CPU ticks, also split by core tier (`hw.perflevelN`). Process CPU uses libproc time counters converted from Mach units with `mach_timebase_info`, then divided by measured elapsed time and active core count; the undivided rate marks a process holding a whole core. Power is the change in each process's `ri_energy_nj` (rusage v6), labelled an estimate. Memory composition and swap come from `host_statistics64` and `vm.swapusage`, network throughput from `NET_RT_IFLIST2`, GPU use from IOAccelerator statistics, and keep-awake reasons from `IOPMCopyAssertionsByProcess`. A live regression test compares this result to `getrusage` process CPU time. Network use by app comes from macOS's private NetworkStatistics framework, which `nettop` reads: Pith loads it at run time, adds each socket's bytes sent and received to its process, and leaves the column out when the framework is missing or has changed. Connections already open count from their first report, not their lifetime, and each sample waits up to 250 ms for fresh counts, which took 5 ms typically. Memory is the sum of member processes' physical footprints, **not unique RAM**; shared pages can be counted more than once. The undocumented memory-pressure sysctl is capability checked, with unknown values shown as unavailable. Protected processes are explicitly counted as unavailable rather than assigned zero usage.

Helpers are grouped only when their executable bundle and process ancestry establish the same owner. Process identities include their start times, which Quit and Force Quit check again just before signalling, since macOS reuses PIDs. App history retains sample-time membership, CPU, footprints, power and read/write counter rates. Individual process counters are a live drill-down. The live history is in memory, lasts ten minutes and expires against continuous monotonic time across sleep. With Keep a week of history turned on in Settings, Pith also keeps 30-second buckets for six hours and 5-minute buckets for seven days, each with its busiest apps, what each wrote to disk and the apps seen opening, in `~/Library/Application Support/Pith/history.json`. Disk's list of who wrote the most is that count: macOS doesn't say which folders a process wrote to, so it's what was writing while the folder grew, not proof of what grew it. Sampling pauses during sleep and restarts with a fresh baseline. Missing counters and gaps remain visible.

Pith samples every second while Activity is on screen or the panel is open, and every two seconds otherwise, for the menu bar figure and kept history. A sample costs about the same either way: a median of 5.5 ms of sampling on 2026-11-07, with memory, tiers, power, network, GPU, battery and sleep assertions included, across roughly 790 processes on the development Mac, so sampling every second all the time would double Pith's cost in the background. Opening Activity or the panel wakes sampling at once, though never within a second of the last sample, so a rate always covers at least a second. These are measurements on one Mac, not a whole-app CPU or energy guarantee.

The Shortcuts actions are App Intents. Pith builds with SwiftPM, which doesn't extract their metadata as Xcode does, so `build-mac.mjs` has the compiler emit their constant values and runs Xcode's `appintentsmetadataprocessor` on them into `Metadata.appintents`, and fails the build when an action is missing from it.

Updates are [Sparkle](https://sparkle-project.org) 2.10.1, pinned exactly in `Package.swift`. Checking for updates is the only time Pith goes online, and only once the person allows it: it fetches the feed from GitHub without Sparkle's system profile. Sparkle downloads the update, checks its EdDSA signature before unpacking it (`SUVerifyUpdateBeforeExtraction`), accepts only a feed signed with the same key (`SURequireSignedFeed`), checks the new app's Developer ID signature, and installs it when Pith quits. Pith shows all of this in its own window, through a custom user driver (`SparkleUpdater.swift`) that hands each step to `UpdateFlow`, rather than Sparkle's windows, which don't follow Pith's look or writing rules. A check Pith makes by itself never opens a window: what it finds waits as a reminder on the panel's last line, as Sparkle's gentle reminders suggest for apps without a Dock icon. Pith isn't sandboxed, so the build drops Sparkle's XPC services. Automated runs (`--smoke-test`, `--activity`, `--scan`) never start the updater.

Temperature sensors, privileged process control, fan control and automatic cleanup are outside this build: they need a root helper or a private interface that breaks across releases.

## Verification

```sh
pnpm --filter storage build:scanner
pnpm check:pith
pnpm check:storage
cargo test --manifest-path apps/storage/scanner/Cargo.toml
```

Swift tests cover rate resets, positive live footprints, CPU units, PID reuse, exited-app retention, Unicode protocol chunks, wrong protocol versions, bridge origin/frame checks, Trash containment and final-component symlinks, real Rust scan decoding, subprocess cancellation/reuse, stderr diagnostics, the live map's reports, the choice between catching up and walking again, FSEvents' file events with inodes, the scanner keeping a folder current over its pipes, icon keys and their one spelling in a URL, the known places and their fallbacks, and the icon store drawing off the main thread with iCloud downloads off. The scanner's `live_tests.rs` checks the index against a fresh scan, folder by folder, after each of 250 rounds of random changes: files written, appended, moved and deleted, folders made, moved and deleted, clones and hard links, with listings landing in a shuffled order. A second run without clones or hard links never needs the daily check, so every round tests what listings alone do. The CI Mac job also packages and verifies the local app signature.

For a desktop smoke test, provide a disposable folder holding a folder named `sub` and at least one file of 1 MB or more, which the live map lists by name:

```sh
apps/storage/native/.build/Pith.app/Contents/MacOS/Pith \
  --smoke-test /absolute/path/to/fixture /tmp/pith-verification.json
```

This opens real native windows and runs the bundled Rust scanner and WKWebView. It verifies metrics, the panel's size and fit, pause/resume, toolbar bridging, range ranking and Escape, tab switching, rendering, fonts, selection, its icon in light and dark, and what deleting it frees, Bigger Text in the map, the fixture's live map matching a scan of it, following a new file and its deletion by itself, and reopening from its saved index as the next launch would, without walking, then following changes again and stopping as the quit stops it, remote-navigation rejection, web-view and window release, and the bundle's update setup (feed, key, both of Sparkle's stricter checks, and Sparkle trimmed and signed by Pith's team), then quits. It keeps the fixture's map in a temporary folder of its own, never maps the startup disk, never starts the updater, and does not trash files or change login, privacy or update settings. `--activity` opens Activity; `--scan /absolute/path` opens Disk and scans that path; `--probe` prints sampler timings and its own footprint without creating a UI.

To prove an installed copy updates itself, run `pnpm --filter storage test:mac-updates`. It builds a throwaway 0.0.1 and 0.0.2 under the bundle id `app.bruhs.pith.updatetest`, signed with the Developer ID but a test key, serves 0.0.2 in a signed feed at 127.0.0.1, opens 0.0.1 with automatic updates on, and checks that Sparkle replaced it with a valid 0.0.2 once it quit. A second Pith shows in the menu bar for about a minute; the real app, its settings and data, and the keychain's update key are left alone. Run it after changing how Pith is built or signed, and whenever Sparkle changes version.
